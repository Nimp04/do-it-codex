## 3. 논의 내용과 결정 사항 (이유 포함)
- 중간발표 피드백: 풀 리퀘스트 기록이 #18, #25 두 건뿐이라는 지적을 받음
  - 원인: 기능 브랜치 → preview 병합을 팀장 로컬에서 진행하고, preview → main만 풀 리퀘스트로 올렸기 때문
  - 결정: 앞으로 기능 브랜치 → preview도 각자 GitHub 풀 리퀘스트(base: preview)로 올리고 로컬 merge는 사용하지 않음. 리뷰어는 돌아가며 지정
  - 이유: 개인별 풀 리퀘스트·리뷰 기록이 GitHub에 남아야 활동 규칙(각자 주 1회 풀 리퀘스트)으로 인정되기 때문
- 중간발표 피드백: 보고서의 브랜치 보호 관련 표기가 잘못되었다는 지적을 받음
  - 결정: 팀장이 main 브랜치 보호 설정(Settings → Branches)을 확인하고 화면을 캡처해 둠
  - 이유: 최종보고서에서 정정 근거로 사용하기 위함
- 활동 최소 기준 재공지
  - 결정: 이번 주부터 각자 매주 커밋 2회, 이슈 1개(작업 전 등록), 풀 리퀘스트 1개(생성+병합), 리뷰 1회 이상을 채움. 기능이 완성된 팀원도 버그 수정·테스트·리팩터링·문서 작업을 이슈 단위로 나눠 진행
  - 이유: 커밋·풀 리퀘스트·이슈는 개인별 GitHub 기록으로 채점되며, 빈 커밋·의미 없는 이슈는 집계에서 제외되기 때문
- 회의록 활동 로그
  - 결정: 각자 이번 주 커밋·풀 리퀘스트·리뷰·이슈·충돌 해결 횟수를 GitHub에서 직접 확인해 기입하고 점검표를 체크함
  - 이유: 활동 로그가 GitHub 기록과 다르면 회의록 항목 점수에 불이익이 있기 때문
- README·CONTRIBUTING 파이썬 버전 통일(3.12 이상) 반영 여부 확인
  - 결정: 미반영 시 문서 담당이 docs 풀 리퀘스트 하나로 처리
