## 3. 논의 내용과 결정 사항 (이유 포함)
### 중간발표 피드백
- 풀 리퀘스트 기록이 #18, #25 두 건뿐이라는 지적을 받음
  - 원인: 기능 브랜치 → preview 병합을 팀장 로컬에서 진행하고, preview → main만 풀 리퀘스트로 올렸기 때문
  - 결정: 앞으로 기능 브랜치 → main으로 각자 GitHub 풀 리퀘스트를 올리고 로컬 merge는 사용하지 않음. 리뷰어는 돌아가며 지정
  - 이유: 개인별 풀 리퀘스트·리뷰 기록이 GitHub에 남아야 활동 규칙(각자 주 1회 풀 리퀘스트)으로 인정되기 때문
- 보고서의 브랜치 보호 관련 표기가 잘못되었다는 지적을 받음
  - 확인 결과: 보고서 작성 시 오기입이었으며, main 브랜치는 현재 보호 중(풀 리퀘스트 승인 1개 필요)
  - 결정: 최종보고서에서 보호 설정 화면을 근거로 정정
- 활동 최소 기준 재공지
  - 결정: 각자 매주 커밋 2회, 이슈 1개(작업 전 등록), 풀 리퀘스트 1개(생성+병합), 리뷰 1회 이상 철저히 관리. 기능이 완성된 팀원도 버그 수정·테스트·리팩터링·문서 작업을 이슈 단위로 나눠 진행
  - 이유: 커밋·풀 리퀘스트·이슈는 개인별 GitHub 기록으로 채점되며, 빈 커밋·의미 없는 이슈는 집계에서 제외되기 때문
- 활동 로그 맞추는 연습
  - 결정: 피드백 반영 작업을 각자 이슈 → 브랜치 → 커밋 → 풀 리퀘스트 → 리뷰 → 병합 절차로 진행
    - README·CONTRIBUTING 파이썬 버전 통합: 조연우
    - config.py 플레이어 사이즈 통합: 김진우
    - main.py, player.py에서 장애물과 적을 장애물(obstacle)로 통합: 정해원
    - 회의록 작성 및 통합: 장여민
  - 이유: 바뀐 풀 리퀘스트 방식을 작은 작업으로 먼저 익혀 다음 기능 개발부터 활동 기준을 안정적으로 채우기 위함

### 우리 팀 기능 개발 방향
- 아이템(item.py, player.py)
  - 아이템을 먹으면 바로 적용하지 않고, 저장해 두었다가 원하는 때에 사용하는 방식(카트라이더 형식)으로 결정
  - 아이템 3종 확정: 이단 점프(스페이스 입력 시), 고스트(무적, 장애물 구현 후 적용), 플레이어 일시적 소형화
  - HP 시스템은 보류하고, 도입 시 고스트 아이템을 '충돌 후 무적'으로 연계하기로 함
  - item.py는 보유 아이템 관리와 특정 단축키 입력 시 저장된 아이템 순서 변경까지 담당, player.py는 아이템 사용 여부에 따라 player state를 수정
  - 이유: 아이템 효과가 player 상태 변경과 직결되므로 item과 player도 level_design과 player처럼 인터페이스를 미리 맞추며 작업해야 함(중간보고서 협업 문제 재발 방지)
- 레벨 디자인(level_design.py)
  - 적과 장애물은 장애물(obstacle)로 통합: 두 기능이 너무 비슷하다고 판단
  - 장애물 통과 및 player 충돌 판정을 통합하여 제공
  - 기능 발판(움직이는 발판) 추가, 아이템 배치
- 그 외 모듈
  - hud.py: 아이템 저장 칸 위치 및 아이템 표시·변경
  - render.py: 새로 추가된 요소(장애물, 기능 발판, HUD 아이템) 렌더링 등록
  - config.py: 플레이어 사이즈 설정 통합
